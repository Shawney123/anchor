## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | **Vite 5** | 静态产物、`base` 配置简单、构建快 |
| 框架 | **React 18 + TypeScript** | 生态稳、团队易维护；本项目状态不复杂，React 足够 |
| 动效 | **Motion (motion.dev)**，`LazyMotion` + `domAnimation` | 支持 `layout`（树的 FLIP 重排）/`AnimatePresence`（页面与 sheet 切换）；按需加载约 18KB gzip |
| 路由 | **手写 hash 路由**（约 60 行） | GitHub Pages 刷新无 404 问题；避免引完整 router |
| 样式 | **CSS Modules + CSS 变量** | 设计系统的 token 直接落在 `:root`，零运行时开销；不用 Tailwind（避免类名爆炸与构建复杂度） |
| 图表 | **手写 SVG** | 只有树、进度环两种图形，不值得引图表库 |
| 图标 | **Lucide**（按需 tree-shake，约 30 个） | 线性风格统一，MIT |
| 存储 | **IndexedDB**（自写薄封装，约 60 行） | 不引 `idb` 也够用；事件日志天然适配 |
| PWA | **vite-plugin-pwa**（Workbox） | manifest + 预缓存 + 版本提示；`registerType: 'prompt'` 手动更新 |
| 部署 | **GitHub Actions → GitHub Pages** | 用户指定静态托管 |
| 测试 | **Vitest**（领域层）+ **Playwright**（关键流程） | 领域层是纯函数，测试成本极低 |

### 2.1 明确不引入
- ❌ 后端 / Serverless / 数据库（GitHub Pages 静态托管，无从部署）
- ❌ 账号体系、OAuth、云同步
- ❌ Web Push（VAPID 需要服务端发送端）
- ❌ 第三方埋点（隐私承诺需要可自证；如需统计，用自托管 Plausible 或干脆不做）
- ❌ CSS 框架、Tailwind、组件库（设计系统自建，避免风格污染与包体膨胀）

## 3. 存储设计

### 3.1 事件溯源（核心决策）

**所有状态变化都写入 append-only 事件日志；当前状态由事件重放投影得出。**

这让三个关键需求变成**结构性保证**而非逻辑补丁：

| 需求 | 如何被保证 |
|---|---|
| 崩塌后重建不丢熟练度 | 熟练度是独立字段，只增不减，事件重放自然保留 |
| 国策树栈式回滚 | 熄父节点 = 追加一条 `policy.extinguish{cause:'parent'}` 事件；子孙由投影规则推导 |
| 判例永久性 | 豁免是事件，投影时构造 `allowedBehaviors` 集合；无撤销事件即不可撤销 |

### 3.2 事件类型

```ts
type EventType =
  // 链
  | 'chain.create'      { chainId, anchorId, taskText, criterion }
  | 'chain.start'       { chainId, at }
  | 'chain.node'        { chainId, nodeNo, durationMs }
  | 'chain.end'         { chainId, nodeCount }
  | 'chain.reset'       { chainId, reason: 'violation' }
  // 预约
  | 'booking.create'    { bookingId, signal, delayMin }
  | 'booking.immediate' { bookingId }
  | 'booking.defer'     { bookingId }
  | 'booking.missed'    { bookingId }
  // 判例
  | 'precedent.grant'   { behaviorKey }        // 永久，全局
  | 'precedent.log'     { chainId, behaviorKey }  // 今日放行记录
  // 国策
  | 'policy.create'     { policyId, ... }
  | 'policy.light'      { policyId, parentId }
  | 'policy.extinguish' { policyId, cause: 'violation'|'parent'|'group'|'manual'|'expiry' }
  | 'policy.freeze'     { policyId, until }
  | 'policy.thaw'       { policyId, satisfied: boolean }
  | 'policy.level'      { policyId, from, to }
  | 'policy.rename'     { policyId, fields }
  // 组
  | 'group.create'      { groupId, faultTolerance }
  | 'group.membership'  { groupId, policyId }
```

### 3.3 投影规则（关键几条）

```
allowedBehaviors  = Set(precedent.grant.behaviorKey)          // 全局永久
chainViolated     = 存在 chain.reset 事件
chainNodeNo       = chain.start 之后 chain.node 计数（reset 后归零）

policy.state:
  frozen        ← 存在未到期的 policy.freeze
  extinguished ← 存在 policy.extinguish，且其因 ancestor 熄灭而级联
  lit          ← 存在 policy.light 且未被 extinguish
  candidate    ← 无 light 事件

policy.habituation = Σ(每次成功结算的权重)  → 0..100，单调不减，跨崩塌保留
policy.level      = L0..L3；失败降一级，L0 即视为熄灭

group.state = lit 当且仅当 组内 extinguished 数 ≤ faultTolerance
```

### 3.4 存储与性能

- `events` store：`autoIncrement` 主键 + `ts` 索引。预估 50 事件/日 → 1.8 万条/年，IndexedDB 完全无压力。
- **快照机制**：每累积 500 条事件或每 7 天，写一次 `snapshot`（含投影状态 + 已消费事件序号），启动时读快照 + 重放增量。避免长期重放拖慢冷启动。
- 启动预算：**首屏可交互 < 600ms**（中端 Android，warm start）。
- **数据导出/导入**：单文件 `.json`（`{v, exportedAt, events[], settings}`），带版本号与 schema 校验。导入前校验、失败给出明确原因、导入前自动备份当前数据。
- **月度备份提醒**：本地记录上次导出时间，超过 30 天在设置页提示（可关闭）。

## 4. 判例引擎

### 4.1 判定流程

```
用户在链中判定一次中断，behaviorKey = "中途看微信"
  ↓
behaviorKey ∈ allowedBehaviors ?
  ├─ 是 → 提示"该行为已永久允许"，直接放行 + 写 precedent.log
  └─ 否 → 弹出判例二选一
            ├─ 判定违规 → chain.reset → 链清零
            └─ 永久允许 → precedent.grant（不可撤销）→ 放行 + precedent.log
```

### 4.2 全局性与不可撤销

- `allowedBehaviors` 是**全局**的，作用于所有链、所有未来——因为原文的逻辑是"规则约束的是行为本身"。
- **单条豁免不可撤销**（这是"永久"的定义，也是这个机制的全部价值所在）。
- 提供**全局重置**「清空全部永久豁免」：一次性删除所有 `precedent.grant` 事件的效力（以补偿事件 `precedent.resetAll` 实现，而非物理删除，保持事件日志 append-only 性质）。代价是所有受影响链的判定标准收紧，可能引发崩塌——**这是有意的摩擦**。

### 4.3 不可豁免清单（已确认接受）

```ts
const NON_NEGOTIABLE = [
  '开车时使用手机',
  '链进行中饮酒',
  '链进行中入睡',
  '跳过必要的就医或服药',
]
```

- 这些行为出现在判定弹层时，**不提供"永久允许"选项**（该选项位置显示为不可用并说明原因）。
- 仍提供「标记为不可抗力」→ 触发水密隔舱流程（冻结相关国策结算），避免用户被硬性卡死而无出路。

## 5. 国策树

### 5.1 数据
树 = 邻接表（`parentId`），不做真正的树结构存储（支持拖拽换挂更简单）。

### 5.2 栈式回滚（原文规则）
```
policy.extinguish{policyId, cause:'violation'} 写入
  ↓ 投影
该节点所有子孙 → state = 'extinguished', cause='parent'
  ↓
子孙的熟练度、等级、点亮历史 **全部保留**
```
### 5.3 分级降级（已确认接受的加固）
```
L0（熄灭） → L1 → L2 → L3
失败时 level -= 1；降到 L0 才算熄灭（等同 extiguish）
主动"升级"：level += 1（需用户显式操作，作为奖励性操作）
```
**为什么需要**：原文的"作息储备计划"已隐含这个模式（+1/+2 强化，出事退回 +0）。泛化后可显著降低崩塌痛感，同时不破坏"一损俱损"的原始语义——**链条仍然清零，只是国策本体的损失被缓冲**。

### 5.4 每日一点亮
- 硬约束：同一天最多一个 `policy.light` 事件（业务规则层强制，非 UI 限制）。
- 默认父节点 = 昨日点亮的国策；用户可改挂。

## 6. 本地候选引擎（无 AI 的国策设计）

纯规则 + 模板，可离线运行，输出与 AI 共演**同构**的候选卡。

### 6.1 算法

```
输入：问题自由文本（+ 可选场景标签）

① 要素抽取
   行为动词：中文动词表匹配（刷手机/拖延/熬夜/吃饭/洗澡/起床/工作/学习/运动…）
   场景：时间词（晚上/睡前/早上/上班）+ 地点词（沙发/床上/办公室/家）
   后果：负面结果词（后悔/焦虑/来不及/精神差）

② 检索定式库
   tag 重叠 + 关键词打分 → 召回 top 30

③ 三类分解（原文 §19）
   a. 堵入口：为该行为生成上游节点候选（"在 X 之前先做 Y"）
   b. 降切换：取阶梯模板（A → A₁ → A₂ → A₃），从最易的一步开始
   c. 借环境：按力量类型检索（因果链 / 行为惯性 / 物理姿势 / 生理本能 / 数学结构）

④ 转成国策卡草案
   trigger 优先取事件锚（回家进门 / 吃完饭 / 结束工作），其次时间锚
   criterion 用原文口径（"以最好的状态专注" + 可选补充条款）
   type ∈ {passive, semi_passive, active}
   est_resistance / est_leverage / est_maintenance ∈ {high, medium, low}

⑤ 排序
   score = w_type[type] × w_resistance × w_leverage
   w_type: passive 0.9 / semi_passive 0.8 / active 0.4     ← 攻略三：主动型降权
   输出 top 3，附一句 rationale："借用了行为惯性 / 回溯到上游节点"
```

### 6.2 定式库结构

```ts
interface Pattern {
  id: string
  name: string
  type: 'passive' | 'semi_passive' | 'active' | 'mechanic'
  tags: string[]                    // 场景标签
  trigger?: { kind: 'event'|'time'|'state', spec: string }
  criterion?: string
  lever: 'high'|'medium'|'low'
  resistance: 'high'|'medium'|'low'
  maintenance: 'high'|'medium'|'low'
  force?: '因果链'|'行为惯性'|'物理姿势'|'生理本能'|'数学结构'
  source?: string                   // 出处（原文 / 用户自建 / 社区）
  difficulty: 'easy'|'medium'|'hard'
}
```

首批内置 **30–50 张**，直接取材原文的现成例子：
先发制人 / 夜幕降临 / 预备仪式 / 电子宵禁 / 陷阱规避 / 神清气爽 / 快速洗碗 / 赢麻了 / 水密隔舱 / 储君继承制 / 二次预约信号 / 侦查任务 / 憋气上浮 / 站着玩手机 …

## 7. AI 共演（零后端、零密钥）

### 7.1 流程
```
产品生成提示词（可复制） → 用户粘贴到任意 AI → AI 返回 JSON → 用户粘回 → 产品校验 → 生成候选卡
```

### 7.2 提示词模板（生成器实现）

```
你是「自制力协议」系统的策略顾问。依据如下方法论，为用户设计 2-3 个可长期执行的"国策"。

【方法论要点】
1. 价值模型：行为倾向 = ∫ V(τ)·W(τ)dτ。W 在近期极高、远期趋零。
   因此远期奖励/远期惩罚几乎无效；必须在近期改变 V 或平移决策时点。
2. 切换成本 ≈ 在 τ=0 插入负向冲激。降低一次切换的难度比硬扛更有效。
3. 三原理：神圣座位（实体锚 + 工作量证明）、下必为例（判例法，一次允许永久生效）、
   线性时延（预约信号，把决策平移到 W 平坦区）。
4. RSIP：只对"有效干预节点"（自由意志尚可干预处）施加约束；有效策略必须能
   跨尺度存活。只做减法、只挂靠必然发生的事件、被动/半被动优先。
5. 设计原则：傻瓜国策 / 农村包围城市 / 不战而屈人之兵 / 化整为零（组 + 容错名额）/
   崩塌即调试器。

【输出格式】严格 JSON：
{"policies":[{"name":"","type":"passive|semi_passive|active",
"trigger":{"kind":"event|time|state","spec":""},
"criterion":"","lever":"high|medium|low","resistance":"high|medium|low",
"maintenance":"high|medium|low","rationale":"（一句话：借用了什么力量/回溯到哪个上游节点）"}]}

【禁止】不要输出鸡汤、远期奖惩、意志力叙事、连续打卡式目标。
【约束】type 优先 passive / semi_passive；trigger 优先 event。

【用户问题】{用户输入}
```

### 7.3 校验
- JSON 解析 + 字段枚举校验 + 必填校验；失败时给出具体字段错误，允许重贴。
- 通过校验的候选卡进入"候选"，由用户**手动点亮**（不自动写入树）。
- 校验通过的卡可"收藏进定式库"（存本地），并可导出分享。

## 8. 通知与提醒（静态托管下）

| 通道 | 实现 | 可靠性 | 说明 |
|---|---|---|---|
| 页内倒计时 | `setTimeout` + 环形进度 + 全屏轻闪 | 高（页面需存活） | 主要通道 |
| 页面常亮 | Wake Lock API，链进行中持有 | 高 | 避免锁屏错过到点 |
| 系统日历/闹钟 | 生成 `.ics`（`VALARM TRIGGER:PT0M`，本地时区 + `TZID`） | 最高 | 兜底通道；用户需手动打开下载的 .ics（2–3 步），首次使用时引导一次 |
| 剪贴板退化路径 | 复制提醒时间 + 一行操作提示 | 中 | .ics 失败时的备选 |
| Service Worker 通知 | `showNotification` | 中（页面关闭后不可靠） | 仅在 SW 存活时有效，作为补充 |

> 诚实说明：纯静态托管**无法实现可靠的后台推送**。这是本方案最明确的能力边界，README 与产品内"方法论出处/关于"页都应写明，而不是让用户以为是 bug。

## 9. PWA 与部署

### 9.1 PWA 配置
- `manifest.webmanifest`：`name: "Anchor 自制力协议"`，`display: standalone`，`theme_color: #0B0E14`，`background_color: #0B0E14`，`orientation: portrait`，图标 192/512 + maskable。
- Service Worker：预缓存应用外壳与字体；`navigateFallback` 到 `index.html`。
- 更新策略：`registerType: 'prompt'` + 应用内"发现新版本"提示条（避免用户卡在旧版行为逻辑上）。

### 9.2 部署（GitHub Actions）

```yaml
# .github/workflows/deploy.yml
on: { push: { branches: [main] } }
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    permissions: { contents: read, pages: write, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build          # vite build → dist/  (base: '/anchor/')
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }
      - uses: actions/deploy-pages@v4
```

关键配置：
- `vite.config.ts` → `base: '/anchor/'`（**必须与仓库名一致**；改名需同步改）。
- 仓库根加 `.nojekyll`（避免 Jekyll 处理 `_` 开头文件）。
- Pages 设置：Source = GitHub Actions。

### 9.3 路由
- **hash 路由**：`#/today` `#/tree` `#/ledger` `#/diagnose` `#/chain`。
- 刷新任意路径均可命中 `index.html`，无需 404 回退配置。

### 9.4 域名
- 默认 `https://<user>.github.io/anchor/`
- 后续可绑自定义域名（CNAME 文件），不影响技术方案。

## 10. 性能预算

| 指标 | 目标 | 手段 |
|---|---|---|
| 首屏 JS（gzip） | ≤ 120KB | React 45 + Motion(LazyMotion) 18 + 应用码 40 + 路由 2 |
| 字体（自托管） | ≤ 90KB | 拉丁子集 + Inter 可变字体单文件 |
| LCP | ≤ 2.0s（中端 Android / 4G） | 预渲染外壳、字体 swap、路由级懒加载 |
| CLS | ≤ 0.05 | 固定尺寸的进度环/树节点占位，避免字体回流 |
| 滚动帧率 | 60fps | 只动 transform/opacity；长列表 `content-visibility` |
| 冷启动到可交互 | ≤ 800ms | 快照 + 增量重放 |

## 12. 待确认的技术细节（评审时逐条过）

1. **ICS 兜底的交互成本**：需 2–3 步手动操作，是否接受？备选是只保留页内倒计时 + Wake Lock（但用户切走 App 就失效）。
2. **Web Share 分享内容边界**：确认只分享国策与定式，不含失败率/中断历史/熟练度百分比。
3. **稳态诊断的实现方式**：规则 + 启发式（离线、可控、零成本）还是接入 LLM（更准但需要密钥 → 与静态托管冲突）。建议先做规则版，AI 共演做补充。
4. **是否提供"多设备同步"路线**：纯静态下唯一低成本的方案是导出 .json 文件手动传输（或未来接第三方 KV 如 Supabase）。是否在 Roadmap 中保留位置。
